# 策略前向说明（cat_policy）

> `cat_policy.c` / `cat_policy.h` / `policy_weights.c` 的实现依据与实测数据。
> 代码注释只留「是什么 + 关键约束」，过程和数字放这里。
> 2026-09-27 建立（做性能优化时顺手把依据落下来）。

## 1. 网络与量化

```
OBS_DIM(59) → 512 → 256 → 128 → 24
前三层 swish(x)=x/(1+e^-x)，头层 24 维里取【前 12】过 tanh 当动作
```

每层公式（int8 权重 + 按【输出通道】的 float scale）：

```c
out[o] = (Σ_i in[i] × W[i][o]) × ws[o] + b[o]
```

- `W` 是 `(in_dim, out_dim)` **行主序**（按 `(out_dim, in_dim)` 读 = 转置乘法，输出全错且不报错）。
- 输入是**归一化后的 float**（±1 上下），不能取整——取整会把小数全变 0。
- bias 只加一次，且**不乘** ws。
- 权重由 `tools/npz_to_c.py` 从 `.npz` 生成 → `policy_weights.c`；`POL_BUILD_ID` = npz 的 md5 前 12 位（溯源用）。
- ⚠️ **口径配套**（2026-09-28 起）：`policy_weights.c` 必须与固件的动作口径**同代**
  （现为「翻身版」`q = clip(act×scale, lo, hi)`，见 `观测组装说明.md`(十)）。
  工程里当前那份 = **v31 = 旧口径**（`q = 默认站姿 + a×0.75`）——**烧录真机/跑 SIL 验收前必须换成翻身版口径的策略**。

## 2. ⚠️ 关键约束：本文件必须 -O2

工程**全局编译在 -O0**（Keil 默认，一直没改过；`.dep` 里可见 `-g -O0`）。
**-O0 下单这一层就要 26.3ms，吃掉整拍 84%** —— 这是 2026-09-27 排查的结论。

处理：给 `cat_policy.c` **单独**挂 `-O2`（工程 per-file 选项，
`<FileOption><FileArmAds><Cads><Optim>3</Optim></Cads></FileArmAds></FileOption>`），
其余文件保持 -O0。改完 `.dep` 里核对过：`cat_policy.c = -O2`，其余 11 个 `.c = -O0`。

| 版本 | 内层指令数 | 周期/MAC | `policy_run` | 整拍周期 |
|---|---|---|---|---|
| 改前（-O0，逐 o 累加）| 12 条/MAC | 22 | 26.29 ms | 35.56 ms |
| 第一步（-O2 + 4 分块）| 6 条/MAC（24 条/4 MAC）| 12.4 | 14.53 ms | 20.07 ms |
| **第二步（-O2 + 8 分块 + uint32 循环变量）** | **4.375 条/MAC**（35 条/8 MAC）| **10.9** | **12.78 ms** | **20.00 ms** |

- 每一步都多次读数一致（14.53 三次 / 12.78 三次）；20.00ms 是"两次读数取差"算的（`Δms/Δloops`）
- 忙碌 31.35 → 19.56 → **17.80 ms** → **余量 0.5 → 2.2 ms**
- ⚠️ **别把优化等级调回去**。若在 Keil GUI 里改 Options 后保存，注意别覆盖掉这一条
  （`--split_sections` 下本文件是独立 `.o`，只影响它自己）。

**为什么到 12.78ms 就下不去了（这条路到底了）**：每个权重的转换链
`LDRSB(取 int8) → VMOV(核→FPU) → VCVT(转 float)` + `VMLA(累加)` = **4 条/MAC，一条都省不掉**
（M4F 没有 int8 SIMD）。分块只能挤掉**循环开销**（2 条/MAC → 0.375 条/MAC），
所以实测只降 12%（指令数降 27%）—— **10.9 周期/MAC 的瓶颈已经是那 4 条的流水**。
再快只有两条路：**把网络变小**（蒸馏，MAC 数直接除十几）或**换 CMSIS-NN int8**
（激活也整型，`SMLAD` 2 个 MAC/周期）；后者必须先跟训练侧的 int8 参考逐层对拍 —— 见 `cat_policy.c` 文末「对拍要求」。
- 试过没用：`-Otime` / `-O3` 只把代码撑大（448 → 476/456 字节），不采用

## 3. 循环为什么这么写（o 方向「分块」：一次算好几个输出）

原写法 `for(o) out[o] += xv * row[o]`：每个 MAC 都对 `out[o]` 做「读-改-写」
（实测反汇编：`VLDR out[o]` → `VMLA` → `VSTR out[o]`，12 条指令/MAC）。

改成 o 方向**一次算 4 个 / 8 个输出**（先 4、后改 8）：

- 一组 8 个累加器（`a0..a7`）是局部变量，-O2 下**住 FPU 寄存器** → 一组只在块末写一次 `out[]`
- 内层 `i` 循环里 `row[0..7]` 是 Flash 里**连续 8 字节**（一次取指就覆盖）
- **每个输出的求和顺序与原写法完全一致**（按 i 升序、从 0 累加、最后 ×ws+b）→ 数值不变（对拍无差异）

| 分块宽度 | 热循环 | 条/MAC |
|---|---|---|
| 不分组（原写法）| （-O0 时）12 条/MAC | 12.0 |
| 4 分块 | 24 条 / 4 MAC | 6.00 |
| **8 分块（现在）** | **35 条 / 8 MAC** | **4.375** |
| 16 分块 | 67 条 / 16 MAC | 4.19（代码 748B，且累加器挤爆 FPU 寄存器 → VPUSH/VPOP 存栈，不值）|

⚠️ 两个细节别被"顺手改回去"：
- **循环变量用 `uint32_t`**：`uint16_t` 会让编译器每次迭代多插一条 `UXTH`（截断）—— 8 分块 36 条 vs 35 条就差在这
- 分块不能无限加宽：M4F 只有 s0–s15 用着方便，16 个累加器就得存栈

## 5. ⚠️ 耗时探针依赖 CYCCNT（踩过的坑）

`main.c` 的分段耗时读 `DWT->CYCCNT`；使能代码在 `servo_init`（`DEMCR.TRCENA` + `DWT_CTRL.CYCCNTENA`），
**开机只设一次**。

2026-09-27 实测：**烧录/调试流程跑完后，设备上 `DEMCR = 0`（TRCENA 被清）** →
CYCCNT 不走 → 观测区 6 个耗时 + `t_all` 全读 0（当时误判成「打点没编进固件」），
而且 `servo_data_recv` 的微秒超时也**永不触发**（`CYCCNT - t0` 恒为 0 → 判超时永远不成立）——
舵机不应答时主循环会**卡死**（IWDG 还没上，没人救）。

**硬复位一次就恢复**（固件自己开机时是设好的），或 SWD 手动写：
`-w32 0xE000EDFC 0x01000000` + `-w32 0xE0001000 0x00000001`。
判据：`-r32 0xE000EDFC 4` = `0x01000000`、`-r32 0xE0001000 8` 的第二字（CYCCNT）在涨，
`DWT_CTRL = 0x40000001` = 正常。

**为什么会变成 0（机制）**：`DEMCR` / `DWT` 属于**调试域**，只有**上电复位（POR）**才清它们，
系统复位不清；但**烧录/调试工具在连接目标时，会按它自己的配置写一遍 `DEMCR`**
（工具的 Trace 没配就是写 0）。关键是顺序：这个写发生在**固件已经跑完启动代码之后**
（工具是"附加上去"的），而固件只在 `servo_init` 里写一次 → 之后没人再写 → 就一直哑着。
**所以"复位一下就好"的本质是：让固件重跑一遍启动代码、自己重新打开。**
旁证：手动用 SWD 写进去之后，后续的只读连接和复位都不会把它清掉 —— 只有下载/调试会话才会。

→ **怎么办（煜辰定的，2026-09-27）**：**不加代码** —— 每次**烧录 / 进调试会话后点一次复位**即可
（复位会让固件重跑 `servo_init`、重新打开秒表）。识别征兆：magic 正常，但 6 个耗时 + `t_all` **全 0**。
（原先想的"开机自检 + 观测区标志 + 每拍自愈"按"最小够用"不做，记录在案；
等上 IWDG/安全那一步时再评估 —— 那时"卡死"会变成"看门狗复位"，性质不同。）

## 6. 参考：别人怎么把 RL 策略塞进单片机（2026-09-27 调研）

| 案例 | 硬件 | 网络 | 实测 | 用的招 |
|---|---|---|---|---|
| 四旋翼 NN 控制器（quad_sim2multireal / Crazyflie）| **STM32F405 @168MHz（和我们同款）**| 18→64→64→4，≈5.5K MAC，FP32 | **500 µs/次**，跑 500Hz 环，CPU 25% | 网络本身就小；`-O2 -mfloat-abi=hard`；权重 `const` 放 Flash |
| 微型四足 RL（arXiv 2512.24740）| Cortex-M0 @5MHz | PPO MLP [128,64] | FP32 ≤5Hz → **int8 后 47.6Hz（≈10×）**，模型 1/4 | **int8 量化**（per-tensor / per-feature）+ 按功率预算选步态 |
| 量化 DRL 控低成本四足（ICRA 2026）| **ESP32-S3**（就是我们的桥）| SAC/TD3 量化友好 actor | 只用本体感知 + 片上推理 | 结构按"量化友好"设计 + 量化兼容 GRU |
| 通用 MCU 压缩（industry guide）| 任意 | — | 量化 2~4×；剪枝 1.5~3×；**蒸馏 3~10×** | 量化 / 剪枝 / 算子融合 / 知识蒸馏 |

**换算到我们这儿**：197,120 MAC ÷ 14.53ms = **13.6M MAC/s ≈ 12.4 周期/MAC**，
跟上面那个 FP32 手写网络（≈5.5K MAC / 500µs = 11M MAC/s ≈ 15 周期/MAC）**同一水平**。
→ **"手写内核"这条路余量不大了**；别人也不是靠手把大网络写快，而是：

1. **把网络变小**（最有效）。例：59→512→256→128→24 蒸馏到 59→128→64→24 ≈ **17K MAC（1/11）**，
   同样 12.4 周期/MAC 只要 **≈1.3 ms**。代价：要重训/蒸馏 + 重新验证步态。
2. **换 CMSIS-NN 的 int8 全连接**（激活也 int8）：`SMLAD` 做 2×2 分块，理论 ~2 MAC/周期
   （≈84M MAC/s）→ 197K MAC ≈ **2.3 ms**（≈6×）。代价：要 q7→q15 扩展/重排，
   且必须与训练侧 int8 参考对拍（见 `cat_policy.c` 文末「对拍要求」）。
3. 便宜的小刀：`swish` 的 896 次 `expf` ≈ 0.4~0.5ms（换查表/近似）；`tanh` 同理；观测降维。
4. 工具链现成的：TFLM + CMSIS-NN、X-CUBE-AI、microTVM 都能从 `.tflite/.onnx` 直接生成 int8 C 代码。

## 7. 参考（二）："走 + 起身"文献里是**一套策略**还是**两套**？（2026-09-27 调研）

**两派都有真机验证的项目**：

| 派别 | 代表工作 | 怎么做的 |
|---|---|---|
| **单策略**（2024-25 新工作）| All-Terrain Quadrupeds: A Unified Policy for Locomotion, Fall & Push Recovery（IEEE 2025，Unitree A1）| **无手写模式切换**；对比学习 latent encoder 从**本体感知历史**推断地形/扰动；课程 + 域随机化 |
| | LocoRec-NP3O: Unified Safe RL Integrating Locomotion and Adaptive Fall Recovery（IEEE 2025）| 统一策略，复杂地形 **<3s** 自主恢复 + 安全协议 |
| | Unified Walking/Running/Recovery for Humanoids via State-Dependent AMP（2025，Unitree G1）| 双判别器（恢复 + 速度条件化），**用 projected gravity 的固定阈值在训练时路由** → "无需运行期模式管理" |
| **多策略 + 仲裁**（更早、更稳）| ANYmal: Robust Recovery Controller（Lee/Hwangbo/Hutter, 2019）| **3 个行为策略 + 1 个选择器 = 4 个网络**，各自单独训；任意倒姿 <5s，**>97%** |
| | ARS（Biomimetics 2024，AiDIN-VIII）| **先**分层多网络（自扶正 + 站立 + 选择器）→ **再蒸馏成一个网络**（PPO + imitation loss）；5s 内从任意姿态（含全翻）起 |
| | HumanUP（RSS 2025，G1）/ HoST（RSS 2025）/ Hifar | 起身**单独一个策略**；两阶段课程：先无约束发现轨迹 → 再在**完整碰撞模型**下精炼成"慢而稳"的可部署动作 |
| | FRASA（2024，RoboCup 冠军队）| 单 agent 同时管 fall recovery + stand up（Cross-Q）|

**四条能直接抄的教训**：

1. ⭐ **"单策略"靠的是训练时的门控/判别器，不是运行期状态机** —— 也就是"训练时状态切换"，文献里就是主流做法。
2. ⚠️ **单策略普遍依赖"本体感知历史"**（latent estimation / obs 堆叠）：要靠历史推断"我现在是倒了还是站着"。
   我们是**单帧 59 维、无历史**（且已知"单帧下速度不可观测"）→ 走单策略路线**要加历史缓冲**（固件也跟着加）。
3. **起身必须精确建模接触几何 + 奖励更稀疏**（HumanUP 原文）→ 正好解释 SIL 里 `fullcontact` 只有 33%。
4. **奖励隔离**：G1 的 gait-conditioned 单策略用 one-hot 步态 ID + **只激活相关奖励项**，避免多任务互相拖累。

**对我们的结论**：**先走 ARS 那条路** —— 多网络分层（各自独立训、独立验收）→ 最后再蒸馏成单网络。
第一版现在的"路由器 + 开环表"就是这套的分层雏形，只差把子动作换成闭环策略。

## 8. 权重来源与在线更新（2026-09-29 加）

策略权重不再直接引用常量 —— 改为运行时的"参数集指针"（`pol_set_t`）：

- `policy_select()`（开机一次 / 每次 OTA 完成后调）：扫槽 A/B（`0x080C0000` / `0x08080000`，
  各 256KB，槽头 72B）→ 全验（magic / 维度 / pose_hash / 全量 CRC32）→ 取"有效且 seq 最大"者；
  无有效槽 → 回退出厂常量（`cat_config.h` 的 `CAT_POL_FACTORY=1` 时；=0 则进"无策略待机"）。
- ⭐ **2026-09-30 更新：现役 `CAT_POL_FACTORY = 0`（「无出厂」终态）**——policy_weights.c 已移出
  Keil 工程（RO-data 206KB → 1.2KB，省 ~205KB）；SIL 构建靠 `-DCAT_POL_FACTORY=1` 跑它自带的权重
  （build_host2.py，别删该旗标；`cat_config.h` 的宏必须 `#ifndef` 包住才能被 `-D` 覆盖）。
- 前向 `policy_run()` 只读 `s_pol.*` 指针 —— **`dense_s8` 与归一化一字未动**（改组后 SIL 对拍：
  与改组前逐位一致，dx +6.79m/18s）。
- 静态初值 = 出厂常量（`CAT_POL_FACTORY=1` 时）/ 空集（=0 且槽未扫描时，靠 `!policy_ready()` 闸"不调用"兜底）；防"select 从未被调用"时空指针 —— 第一版的教训，别删。
- 槽格式/帧/时序 → `通信协议.txt` 第七章；实现 → `cat_polupd.c/h`、`cat_pose.c/h`
  （姿态/限位表 2026-09-29 从 cat_obs.c 抽出为系统常量，与策略解耦）。
