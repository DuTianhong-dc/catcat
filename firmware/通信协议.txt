【注意】配置 GPIO 寄存器必须用「读-改-写」，禁止整体赋值。
原因：一个端口（如 GPIOC）的 16 个引脚共用同一套配置寄存器，整体赋值（如 GPIOC->MODER = 0x00000000;）
会把同端口其他引脚的配置一起冲掉。PC6/PC7 已配给 USART6，一旦被冲掉本通道立即失效，
而症状与本通道代码毫无表面关联，极难定位。正确写法：GPIOC->MODER = (GPIOC->MODER & ~掩码) | 新值;

**一：舵机与开发板之间的通信：
硬件接线是：开发板PC6/7连接驱动板TX/RX，共地，驱动板信号引脚接12个舵机的信号线，
所以开发板到驱动板是异步全双工，驱动板到舵机是异步半双工，由于舵机只能被动应答，所以均可以看作全双工通信，
驱动板仅作为桥。
控制器发出指令包，舵机控制器和舵机之间采用问答方式通信，控制器发出指令包，舵机返回应答包。
内存表的部分参数采用两个字节的值域时，两个字节分别表示高字节与低字节，该系列是低字节在前高字节在后。
秉持物尽其用的原则我们希望尽可能的对舵机的通信方面进行开发，
（1.1）指令包：
1、指令包结构
字头      ID号  数据长度 指令         参数                        校验和
0XFF 0XFF ID    Length  Instruction  Parameter1 ...Parameter N  Check Sum
2、字头：连续收到两个 0XFF ,表示有数据包到达。
3、ID 号: 每个舵机都有一个 ID 号。ID 号范围 0～253,转换为十六进制 0X00～0XFD。广播 ID: ID 号 254 为
广播 ID,若控制器发出的 ID 号为 254(0XFE)，所有的舵机均接收指令，除 PING 指令外其它指令均不返回应答信
息(多个舵机连接在总线上不能使用广播PING 指令)。
4、数据长度：等于待发送的参数 N 加上 2，即“N+2”。
5、指令：数据包操作功能码，详见 1.3 指令类型。
6、参数：除指令另外需要补充的控制信息，参数最大支持双字节参数表示一个内存值，字节顺序参考舵机使用手册内
存控制表(不同型号舵机字节顺序不一样)。
7、校验和：校验和 Check Sum，计算方法如下
Check Sum = ~ (ID + Length + Instruction + Parameter1 + ... Parameter N) 若括号内的计算和超出 255
, 则取最低的一个字节，“~”表示取反。

（1.2）应答包
1、应答包结构
应答包是舵机对控制器的应答，应答包格式如下：
字头       ID 号 数据长度 当前状态  参数                        校验和
0XFF 0XFF  ID    Length   ERROR   Parameter1 ...Parameter N   Check Sum 
2、返回的应答包包含舵机的当前状态 ERROR，若舵机当前工作状态不正常，会通过这个
字节反映出来（各状态所代表意义详见手册内存控制表），若 ERROR 为 0，则舵机无报错信息。
若指令是读指令（READ DATA），则 Parameter1 ...Parameter N 是读取的信息。

（1.3）指令类型
指令                    功能                                值         参数长度
PING（查询）            查询工作状态                        0x01          0
READ DATA（读）         查询控制表里的字符                  0x02          2
WRITE DATA（写）        往控制表里写入字符                  0x03          大于等于1
REGWRITE DATA(异步写)   类似于WRITE DATA，但是控制字符写入   
                        后并不马上动作，直到ACTION指令到达   0x04         不小于2
ACTION（执行异步写）     触发REG WRITE写入的动作             0x05     0
SYCNREAD DATA（同步读）  用于同时查询多个舵机                 0x82        大于等于3
SYCNWRITE DATA（同步写） 用于同时控制多个舵机                 0x83         不小于2
RECOVERY（参数恢复）     把控制表复位为出厂值                  0x06        0
RESET(状态重置)          重置舵机状态(重置舵机圈数)            0x0A         0
二：开发板与驱动板之间的串口（USART6）
（2.1）引脚与接线
1、PC6 = USART6_TX（开发板发→驱动板收），PC7 = USART6_RX（开发板收←驱动板发），两脚均需与驱动板共地。
2、PC6/PC7 上 USART6 的复用功能号为 AF8。这两脚还复用着 TIM8_CH1/CH2、DCMI_D0/D1、SDIO_D6/D7 等，本协议只用 USART6。
3、注意：PC6/PC7 同时接板载 OLED/CAMERA 接口的 D0/D1（PC6 另接 ES8388 的 MCLK），故使用本通道期间不可插板载 OLED 屏或摄像头模块。

（2.2）串口参数
1、波特率 1000000bps（1Mbps，舵机出厂默认值）。
2、一帧 10 位：1 位起始位 + 8 位数据位 + 无校验 + 1 位停止位（8N1），无硬件流控。
3、全双工：开发板侧收发同时进行，方向转换由驱动板硬件完成，开发板不做方向切换。

（2.3）初始化要点
1、USART6 挂在 APB2 上。本工程 SYSCLK = 168MHz，APB2 分频系数 2，故 APB2 = 84MHz。
2、波特率寄存器 BRR = 外设时钟 / 波特率 = 84MHz / 1Mbps = 84，为整数，零误差。
3、PC6/PC7 引脚配置：MODER = 复用、OTYPER = 推挽、OSPEEDR = 高速、PUPDR = 无上下拉、AFR = 8。
4、不加上拉的原因：舵机应答是开漏输出，需要能把总线拉低；经驱动板时总线静默电平由板内上拉保持。若实测总线浮空（收不到数据），再考虑开内部上拉。

三：常用指令的帧格式（实现时逐条对照）
（3.0）通用说明
1、指令帧结构见（1.1），应答帧结构见（1.2），下面只列每条指令的参数怎么填。
2、校验和参与计算的范围：从 ID 开始、到最后一个参数/数据为止；不含两个 0xFF 字头，也不含校验和自己。
3、指令帧长度 = LEN + 4；LEN = 参数个数 + 2。

（3.1）PING（0x01）查询工作状态
1、指令帧：FF FF | ID | 02 | 01 | CK
     无参数，LEN = 0 + 2 = 2。
     例：查 ID1 → FF FF 01 02 01 FB
2、应答帧：FF FF | ID | 02 | ERROR | CK   （共 6 字节，固定长度）
     例：FF FF 01 02 00 FC
     ERROR = 0 表示舵机正常无报错；ERROR 非 0 的含义查舵机内存表（状态位定义）。
3、注意：不要用广播 ID（0xFE）发 PING —— 总线上多颗舵机会同时答应，应答在总线上互相撞车。
   要查哪颗就用它的具体 ID 逐颗查。

（3.2）上电自检怎么查
1、逐颗查 ID 1~12（共 SERVO_COUNT 颗），不用广播。
2、任一颗没应答、或应答帧的 ERROR 非 0，都记入"缺失位图"（bit0=ID1 … bit11=ID12），供上层报警/卸力判断。

（3.3）WRITE（0x03）往控制表写数据
1、指令帧：FF FF | ID | LEN | 03 | 地址 | 数据1 … 数据N | CK
     LEN = N + 3（N 为数据个数）—— 因为参数 = 1 个起始地址 + N 个数据。
     例4：让 ID1 以 1000 步/秒转到 2048，在地址 0x2A 起连写 6 字节
          （位置 0x0800、时间 0x0000、速度 0x03E8）
          → FF FF 01 09 03 2A 00 08 00 00 E8 03 D5
2、应答帧：FF FF | ID | 02 | ERROR | CK（6 字节固定）。
3、广播写法（ID 传 0xFE）：所有舵机都执行，但【都不应答】——此时不能去等应答，否则会死等。
     改舵机 ID 就是这么改的（往地址 0x05 写新 ID）。注意 EPROM 有保护锁开关，
     改之前要先解锁（地址 0x37 写 0），否则掉电不保存。
（3.4）READ（0x02）读控制表

1、指令帧：FF FF | ID | 04 | 02 | 首地址 | 读长度 | CK
     LEN = 4 = 参数个数(2) + 2。
     例2：读 ID1 的位置（0x38 起 2 字节）→ FF FF 01 04 02 38 02 BE
2、应答帧：FF FF | ID | LEN | ERROR | 数据… | CK
     数据跟在 ERROR 后面，低字节在前。LEN = 读长度 + 2，整帧 = 读长度 + 6。
     例2 应答：FF FF 01 04 00 18 05 DD → 位置 = 0x0518 = 1304
3、单次最多读 58 字节（整帧 6+58 = 64，要装进缓冲）。
     整表 0x00~0x45 共 70 字节，一次装不下，要分两段。
     运行时观测只要 0x38 起 15 字节（含电流的两个字节），一次够。

（3.5）SYNC READ（0x82）一条指令读多颗

1、指令帧：FF FF | FE | LEN | 82 | 首地址 | 读长度 | ID1 | ID2 … IDn | CK
     LEN = n + 4（n = 颗数）= 参数个数(2+n) + 2。
     例8：查 ID1、ID2 的 0x38 起 8 字节 → FF FF FE 06 82 38 08 01 02 36
2、应答：每颗各回一帧，格式同（3.4），按指令里给的 ID 顺序返回。
3、注意：LEN 只跟颗数有关（n+4），跟你读多少字节无关 —— 读长度只是 1 个参数。
4、注意：掉线的颗不会应答，不能死等 n 帧；必须靠超时收尾，没收到的记进缺失位图。
5、注意：12 颗的应答合计 276 字节长突发，实测驱动板必丢尾 1~2 字节。
     所以本工程每次只发 4 颗（12 颗分 3 组），实测稳定。

（3.6）SYNC WRITE（0x83）一条指令写多颗

1、指令帧：FF FF | FE | LEN | 83 | 首地址 | 数据长度L | ID1 数据×L | ID2 数据×L | … | CK
     LEN = (L+1)×n + 4（L = 每颗写多少字节，n = 颗数）。
     例7：ID1~ID4 共 4 颗，从 0x2A 起各写 6 字节（位置 0x0800、时间 0x0000、速度 0x03E8）
          → FF FF FE 20 83 2A 06 01 00 08 00 00 E8 03 02 00 08 00 00 E8 03
            03 00 08 00 00 E8 03 04 00 08 00 00 E8 03 58
2、无应答（必须广播 0xFE）—— 发完即止，不能去等。
3、注意：每颗的首地址和数据长度必须相同，所以一条指令里只有一组“首地址+长度”。
4、注意：一定要一条帧把 12 颗写完。同一帧里所有颗同时收完 → 同时启动；
     拆成 6+6 两帧会分成两批先后动作，正好毁掉同步写的意义。
5、本工程 12 颗 × 6 字节 = 整帧 92 字节（缓冲 128 够）；12 颗最多可写 9 字节/颗。
**四、IMU与开发板之间的通信
备注
参数

串口输出频率    默认25Hz，支持10Hz~100Hz可调
IIC时钟速率     100KHz
输出内容        3轴加速度、3轴角速度、3轴角度、3轴磁场、气压、高度、温度、四元数

（4.1）接线与供电
1、接线（**交叉**，别接反）：模块 RX → 开发板 PA2（USART2_TX）；模块 TX → 开发板 PA3（USART2_RX）；
   模块 GND → 开发板 GND；模块 5V → 开发板 5V。
2、模块支持 5V 或 3.3V 供电（见上面规格）。**串口电平按供电走，接线前要确认**，接错可能烧 PA2/PA3。
3、支持串口和 IIC 两种接法（IIC 从机地址 0x23），本工程用串口，参数 115200 8N1。
4、⚠️ 模块**启动时间 5000ms** —— 上电后约 5 秒才开始出数据，初始化后要等着，别误判成掉线。
5、型号差异：**10 轴**磁力计与气压计都有；**9 轴**无气压计；**6 轴**无磁力计也无气压计。本工程用 10 轴。

（4.2）数据帧格式
      包头1  包头2  长度   功能字  数据…        校验位
      0x7E   0x23   XX      XX     XX…          XX
下标  0      1      2       3      4…          末位

1、长度 = **整帧总字节数**（等于校验位的下标加 1）。不是"参数个数 + 2"。
2、校验位 = 从**包头1**累加到校验位前的所有字节，取最低字节。
3、小端：多字节量低位在前、高位在后。
4、单帧最长 40 字节（官方库的接收上限）。

【注意】IMU 的校验位【含包头】，跟舵机的校验和规则不一样：
    舵机 CK = ~(从 ID 开始累加，不含 FF FF 字头)
    IMU  CK = (0x7E + 0x23 + 长度 + 功能字 + 数据…) & 0xFF，含包头
    例：请求固件版本 → 7E 23 07 80 01 00 29
        7E+23+07+80+01+00 = 0x129 → 取低字节 = 0x29 ✓

（4.3）IMU 是"主动上报"的，不是问答式
舵机是问答式：你不问它就不说话。
IMU 不一样：上电后它按设定频率**自己往串口推数据**，默认 25Hz（可用 0x60 改成 10~100Hz）。
所以开发板侧的主要工作是"**收帧 → 校验 → 取最新**"，不需要每拍都发指令；
只有配置类操作（改频率、改算法、校准）才需要主动发指令。

（4.4）功能字总表

下行（开发板 → 模块）：
    0x80  请求数据        参数1 = 要请求的功能字，参数2 = 0x00
    0x60  设置输出频率    参数1 = 频率 Hz（10~100），参数2 固定 0x5F。无返回
    0x61  设置算法类型    参数1 = 6（六轴）或 9（九轴），参数2 固定 0x5F。无返回
    0x70  校准 IMU        参数1 = 0 清除校准值 / 1 开始校准，参数2 固定 0x5F
    0x71  校准磁力计      参数同上
    0x72  校准气压        官方驱动库有此项，协议表未列
    0x73  校准温度        参数1、参数2 = 温度×100（小端），参数3 固定 0x5F
    0xA0  重置用户数据    参数1 = 0x01，参数2 = 0x5F。会把所有校准值清零，慎用

上行（模块 → 开发板）：
    0x01  固件版本        主版本号、副版本号、补丁版本号，各 1 字节
    0x81  返回状态        功能字 + 状态（0 = 失败，1 = 成功）
    0x04  原始数据        加速度 XYZ + 陀螺仪 XYZ + 磁力计 XYZ，各 int16
    0x0A  陀螺仪原始数据  协议表未列，官方驱动头文件里有（单独读陀螺）
    0x10  磁力计原始数据  协议表未列，官方驱动头文件里有（单独读磁力计）
    0x16  四元数          Q0(w)、Q1(x)、Q2(y)、Q3(z)，各 float32
    0x26  欧拉角          ROLL、PITCH、YAW，各 float32，单位是【弧度】
    0x32  气压计          高度(米)、温度(℃)、气压(帕)、参考气压(帕)，各 float32（仅十轴有）

（4.6）数值换算
原始数据（0x04）是 int16 原始值，要乘比例才得到物理量：
    加速度 ACCEL  × 16 / 32767.0                  → 单位 g（量程 ±16g）
    角速度 GYRO   × (2000 / 32767.0) × (π/180)    → 单位 rad/s（量程 ±2000°/s）
    磁力计 MAG    × 800 / 32767.0                 → 单位 uT
欧拉角（0x26）和四元数（0x16）本身就是 float32，不用再乘比例；
欧拉角的单位是**弧度**，要角度得自己 × 57.2957795。

数据区从**下标 4**开始（包头1/包头2/长度/功能字 占了下标 0~3）。
例：欧拉角帧 7E 23 11 26 | R1 R2 R3 R4 | P1 P2 P3 P4 | Y1 Y2 Y3 Y4 | CK
    整帧 17 字节 = 长度字段 0x11 ✓

（4.7）与舵机协议的关键差异（容易搞混，列出来对照）
    项目        舵机 SCS               IMU
    通信模式    问答式（你不问不说）  主动上报（按频率自己推）
    帧头        FF FF                 7E 23
    校验和范围  从 ID 起，不含字头     从包头1 起，含字头
    长度含义    参数个数 + 2          整帧总字节数
    波特率      1 Mbps                115200
    多字节序    低字节在前            低字节在前  ← 这条相同

（4.8）还没确认的点（写驱动前要留意）
1、模块标称支持 5V/3.3V，但**串口 TX/RX 的实测电平**要确认清楚 —— 接错可能烧 PA2/PA3。
2、0x04 / 0x16 / 0x26 三个"自动上报"是同时都发，还是只发其中一个 —— 官方库没写死，
   实际抓一次串口看就知道。
3、发出设置输出频率的 0x60 指令后**没有返回**，无法从协议上确认是否生效，要真机实测。

官方驱动的整体套路：【中断收字节 → 环形缓冲(256B) → 主循环里跑状态机解析】。
状态机 5 步：等包头1 → 等包头2 → 收长度 → 收功能字 → 收数据区(含校验)；
校验通过才解析，不通过丢弃。数据区长度 = 长度字段 − 4。

⚠️ 但它有三处照抄会出事的地方，要改掉：
1、中断服务函数里有一句 while (RXNE == RESET); —— **在中断里死等**。
   中断本来就是 RXNE 触发的，这句多余，而且标志一旦已被清就会**死锁**。
2、它把字节**攒够 127 个才一次性推给环形缓冲**。IMU 一帧才 17~21 字节，
   等于**滞后 6~7 帧**才开始解析；数据流若中途停下，最后那批数永远不被处理。
   → 应改成"**每收到一个字节就推进环形缓冲**"，中断里只做这一件事、尽快返回。
3、它的状态机走到"等包头2"那一步时，只要来的字节不是 0x23 就**直接复位**。
   于是噪声里夹了一个 0x7E、紧跟着又是真正的帧头"7E 23"时：第二个 0x7E 被当成
   "上一个包头1 的第二字节"，发现不是 0x23 → 复位；等真正的 0x23 到来时，状态机
   已经不在"等包头2"了 → **真帧的包头被吃掉，白丢一整帧**。
   → 应改成：那一步如果来的还是 0x7E，就**保持"等包头2"状态**，把它当作新的包头1。


**五：ESP32 与开发板之间的通信（2026/9/25 新增）

本节定的是"上位机 ↔ 开发板"这条链路。它跟舵机(一)、IMU(四)是三条独立的链路，
互不影响：这条断了，猫照样能靠本地策略站住、走路，只是收不到新指令。

（5.1）链路与角色划分
    上位机(手机/PC) --BLE--> ESP32-S3 --UART--> 开发板(STM32)
    1、ESP32 只是【透传桥】：BLE 收什么就往串口转发什么，不做协议解析。
       所以本协议完全在 STM32 侧实现，换任何上位机(只要用 BLE 串口服务)都不用改固件。
    2、BLE 用标准 Nordic UART Service：6E400001-B5A3-F393-E0A9-E50E24DCCA9E
       (RX 特征 6E400002-…、TX 特征 6E400003-…)。LightBlue 这类通用工具能直接连。
    3、ESP32 与开发板之间：USART3 / PB10(TX)-PB11(RX) @115200 8N1。
    4、职责划分：STM32 跑策略与舵机控制(50Hz 本地闭环)；上位机只发指令、收状态。
       上位机【不参与控制环】，所以它卡顿/断连不会让猫跌倒。

（5.2）下行帧：上位机 → 开发板（固定 10 字节）
    字节  内容      说明
     0     0xAA     帧头1
     1     0x55     帧头2
     2-3   vx       前进后退，int16 小端，实际值 = vx / 1000.0 (m/s，正=前进)
     4-5   wz       转向，int16 小端，实际值 = wz / 1000.0 (rad/s，正=左转)
     6     flags    控制位，见下
     7     pan      云台水平，int8，-127~127 映射 0~180 度
     8     tilt     云台俯仰，int8，同上
     9     ck       校验和 = (字节 2~8 累加) & 0xFF

    1、**只有两维指令**：前进后退(vx) + 转向(wz)。没有 vy(侧移)。
    2、flags 只有一位有意义：
         bit0 = 使能。0 = 停止运动(原地站立, 舵机保持出力)；1 = 运行。
       【注意】使能位是唯一的安全开关：上位机断连超过 DEADMAN 时间，固件必须
       自动把使能位视为 0(不让猫"保持最后一个指令一直走下去")。
       ⚠️ "停止" ≠ "卸力"：卸力是舵机 0x28 扭矩开关 = 0，会让舵机断电、猫直接趴下；
          本位的 0 只表示"不执行新的移动指令"，舵机仍保持出力站住。
       ⚠️ DEADMAN 取 1000ms：下行频率 100Hz(2026/9/26 定) → 发送间隔 10ms，
          判据是【发送间隔 × 5】= 50ms。1000ms 相当于允许连丢 100 帧，抗 BLE 抖动很宽。
          这是安全兜底，误触发(猫走得好好的突然停)比晚一秒停更糟，所以宁可放宽。
          固件侧有编译期断言兜着 —— 改了频率不校 DEADMAN 会直接编译报错。
    3、多字节量一律**小端**(低字节在前)，跟舵机、IMU 一致。
    4、校验和不含帧头(AA 55)，从 vx 算到 tilt —— 跟舵机"从 ID 起算、不含字头"同规则，
       跟 IMU"含包头"相反，别搞混。
    5、定点数用 ×1000 而不是浮点：帧更短，且两端不会因为浮点表示差异对不上。

（5.3）上行帧：开发板 → 上位机（状态包）
    字节  内容    说明
     0     0x5A   帧头1
     1     0xA5   帧头2
     2     len    载荷长度(不含帧头/len/type/ck)
     3     type   载荷类型，当前只有 0x01 = 全量状态
     4..   载荷   见下
     末    ck     校验和 = (从字节 0 累加到 ck 前) & 0xFF

    【设计取向】一次把"所有状态"打包发出去，而不是按需查询。
    理由：上位机(含将来的视觉决策)需要完整上下文，逐项查询会产生往返延迟。

（5.4）载荷 0x01：全量状态（当前 86 字节）
    偏移  内容                  类型/换算
     0    运行毫秒               uint32，开机累计
     4    主循环计数             uint32，一直在涨说明没死
     8    FSM 状态               uint8，见状态机定义
     9    故障码                 uint8，0 = 无故障
    10-11 当前 vx(回显)          int16，同下行换算
    12-13 当前 wz(回显)          int16，同上
    14-19 姿态 roll/pitch/yaw    int16 ×3，0.01 度
    20-25 角速度 gx/gy/gz        int16 ×3，0.01 rad/s
    26-28 重力方向(机体系)       int8 ×3，×127 归一化
    29-52 舵机位置 12 颗         int16 ×12，步(0~4095)
    53-64 舵机温度 12 颗         int8 ×12，摄氏度
    65-76 舵机状态位 12 颗       uint8 ×12，位标志(BIT0 电压 / BIT1 磁编码 /
                                 BIT2 过热 / BIT3 过流 / BIT5 过载)
    77-78 云台当前 pan/tilt      int8 ×2
    79-80 电池电压               uint16，0.01V
    81-82 保留                  置 0，将来放"机身速度"(linvel)，需本地估速功能先做出来
    83-85 保留                  置 0
    → 载荷共 86 字节(偏移 0~85)；整帧 = 2(帧头) + 1(len) + 1(type) + 86(载荷) + 1(ck) = **91 字节**。

    1、上行频率 **10Hz**。带宽占用：91 字节 × 10 bit × 10Hz = 9100 bit/s，
       占 115200 的 7.9%，余量充足。
    2、负值一律用补码 int16/int8 表示(如姿态角 -4.5 度 → -450)。
    3、类型字段(type)留着将来扩展：可以再定义 0x02 = 高频精简包(只含姿态+指令回显)，
       给需要更跟手场景时用，不影响现在的 0x01。

（5.5）数值换算与示例帧
    下行示例：vx = 0.5 m/s 前进、wz = 0、使能开、云台中位 90 度
        vx16 = 500 = 0x01F4 → 字节 F4 01
        wz16 = 0
        flags = 0x01(使能)
        pan = tilt = 0 (映射到 90 度中位)
        ck = (F4+01+00+00+01+00+00) & 0xFF = 0xF6
        整帧：AA 55 F4 01 00 00 01 00 00 F6
    上行示例(只列帧头部分)：
        5A A5 56 01 | … 86 字节载荷 … | ck
        其中 0x56 = 86 = len；整帧 91 字节。

（5.6）还没确认的点（写代码前要留意）
    1、ESP32-S3 与 STM32 的实际接线引脚（计划 USART3/PB10-PB11，跟第一版一致），
       以及电平是否 3.3V 直连 —— 上电前要确认。
    2、DEADMAN 暂取 1000ms（理由见 5.2）。下限 50ms 已由编译期断言保证；
       但 1000ms 是否合适，还要等上位机实际跑起来、对着真实 BLE 抖动校一次。
    3、舵机温度/状态位这两段依赖舵机的 0x3E/0x41 寄存器逐颗读取(12 次往返)，
       会占用可观时间；若发现拖慢 50Hz 主循环，需要改成"每拍只读 1~2 颗轮转"。
    4、车身速度(linvel)字段先留 0，等本地位移估计做出来再填。


**六：云台（两个 MG90S 舵机）与开发板之间（2026/9/26 新增）

（6.1）它跟腿上那 12 颗【不是一类东西】
    腿上 12 颗：STS3215 **总线舵机** —— 走 USART6，问答式，有 ID、有内存表(见一、三章)
    云台 2 个 ：MG90S **模拟舵机** —— 一根信号线收 PWM，没有 ID、没有反馈、不会应答

    所以云台【不走 USART6】，也【不能】拿第一章的 SCS 协议去读写它。
    想知道云台当前角度，只能靠"上次发给它的是什么"来回显(见 6.6)。

（6.2）接线与定时器
    PB6 = TIM4_CH1 = pan（水平）    AF2
    PB7 = TIM4_CH2 = tilt（俯仰）   AF2
    参数：50Hz 标准舵机 PWM，周期 20ms，脉宽 500~2500μs 对应 0~180 度
    回中 = 1500μs(90 度)，也是装配时对齐齿轮花的参考位

（6.3）定时器时钟的坑（F4 特有，第一次必踩）
    F4 的定时器时钟 = APB1 × 2 = 84MHz（不是 APB1 本身的 42MHz）
        PSC = 83 → 84M / 84 = 1MHz，即 1μs/tick
        ARR = 19999 → 20ms 周期(50Hz)
    若按 42MHz 去算(取 PSC=41)会得到 2MHz → 脉宽实际减半：
       1500μs 发成 750μs(22.5 度)，满程只剩四分之一，表现为"舵机转不到位"。
    依据：第一版 cat_gimbal.c，2026-09-12 修过这个 bug。

（6.4）脉宽必须硬钳位：CCR 永远不许超出 500~2500μs
    不管哪条路径(坏帧 / 算错 / 将来改动)，都要在写 CCR 前钳死。
    原因：MG90S 是金属齿，遇到超范围脉宽会顶死机械限位持续堵转 → 发热烧线圈。
    （塑料齿的 SG90 顶多打齿，金属齿会硬顶到烧）

（6.5）PB6 的特殊性
    PB6 在 F407 上同时是 I2C1_SCL 的默认复用脚 ——
    必须把 OTYPER / OSPEEDR / PUPDR 全部显式设定，不能只改 MODER 和 AFR。
    残留的开漏配置会让 PWM 变成毛刺，表现为"舵机嘎嘎抖 / 乱转"。

（6.6）在本协议里的位置
    下行：帧[7] = pan，帧[8] = tilt，各 int8，-127~127 映射 0~180 度（见 5.2）
    上行：载荷 +77 / +78 回显当前 pan / tilt（见 5.4）

    只在收到有效帧时更新 —— 失联/急停/维护时【保持不动，不回中】。
    理由：维护模式下手伸在云台里，回中会夹手。
    故障时不保持 —— 故障后反而要靠它保留观察能力，照常跟指令动（2026/9/28 修正）。
    （不是"回中"，是"拒绝新指令保持原位"）

（6.7）型号更正
    第一版 cat_gimbal.h 的注释写的是 SG90 —— 那是过时的。
    实际在用的是 MG90S（金属齿），2026-09-11 换的，cat_gimbal.c 里已写明。

（6.8）待确认
    1、MG90S 的工作电压(常见 4.8~6V)与开发板 5V 供电是否匹配，上电前量一下。
    2、两个舵机同时堵转的电流是否会让 5V 电源跌落，必要时独立供电/加电容。
    3、回中 1500μs 是理论值，实际机械中位要装机后标定。
