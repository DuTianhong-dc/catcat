# 系统层说明（cat_sys.c / cat_sys.h）

> 代码里只留"做什么 + 关键约束"，为什么这么做记在这里。

---

## 一、这个文件的定位

**纯系统层**：时钟、时基、观测区。**不依赖任何外设模块**（不 include `cat_servo` / `cat_imu`）。

**为什么单独一个文件**：跟 `cat_servo` / `cat_imu` 一个规矩 —— 每个"硬件/功能"一个模块，
`main.c` 只负责按顺序调它们，不装实现。

**判据**（遇到放哪的疑惑时用）：
> **只跟一个外设打交道的 → 放那个模块；跨多个模块的 → 属于"编排"，放 main。**

（比如"等舵机+IMU 都就绪"跨两个模块，就放在 `main.c` 里而不是这儿。）

以后看门狗（IWDG）、延时、复位原因也归这个文件。

---

## 二、⭐ 为什么必须有 `sys_clock_init()`

### STM32 复位后跑多快？
**不是 168MHz**，而是内部 RC 振荡器 **HSI 16MHz** —— 又慢又不准。

要跑到 168MHz 必须**手动配 PLL**（锁相环倍频）。**HAL 工程靠 `HAL_RCC_OscConfig()` 做这件事；
我们不用 HAL，不配就没人配。**

### 不配会怎样（真踩过，2026-09-25）
所有串口波特率都是**按 APB 频率算出来的**（舵机 `BRR=84` 假设 APB2=84MHz；IMU `BRR=365` 假设 APB1=42MHz）。

时钟跑在 16MHz 时：
- 舵机实际波特率 ≈ **190kbps**（该 1Mbps）
- IMU 实际波特率 ≈ **44kbps**（该 115200）

→ **两个外设一个都连不上**，而且现象看起来完全像"接线坏了 / 舵机没上电"。

**排查手法**：读 `RCC->CFGR` 的 SWS 位，或实测 `DWT->CYCCNT` 的增速。

### 配置流程（4 步）
```
1. 开 HSE(8MHz) 等就绪    —— 起不来就走 HSI 退路(16MHz), 两种源都能算到 168MHz
2. 配 Flash 等待周期      —— 168MHz 要 5 WS + 开预取/缓存(详见下节)
3. 配 PLL                 —— 1MHz 进 × 336 ÷ 2 = 168MHz
4. 切到 PLL + 定总线分频  —— AHB÷1=168 / APB1÷4=42 / APB2÷2=84
```

**参数抄自第一版 `SystemClock_Config()`**（它是 HAL 版，但 PLL 系数一致）。

## 三、为什么 168MHz 要设 5 个 Flash 等待周期

| 供电 | 无等待最高频率 | 168MHz 需要 |
|---|---|---|
| 2.7~3.6V（我们）| 30 MHz | **5 WS** |

（出处：STM32F407 数据手册 Table 15 / RM0090 Table 10；第一版 `FLASH_LATENCY_5` 也是这个）

**⚠️ 但实测性能不受影响**：数据手册同一张表的脚注说 ——
> "Thanks to the **ART accelerator** and the 128-bit Flash memory, the number of wait states
> given here **does not impact the execution speed** from Flash memory"

即 **ART 加速器（预取 + I-Cache + D-Cache）让实际执行等效于 0 等待**。
所以**不需要**把代码搬进 RAM 跑。

**另外两条**：
- 等待周期只管"**从 Flash 取指令**"；**代码从 RAM 执行时本身不需要等待周期**
- `CCM RAM`（`0x10000000`，64KB）是**0 延迟的数据访问内存**（我们用它放观测区）
  —— 局限：**不能被 DMA 访问**

## 四、⭐ 观测区为什么放 CCM，不放 SRAM

```c
dbg_t g_dbg __attribute__((at(0x10000000)));
```

### 因为 ARMCC 的 `at()` 有个坑
**它会从 RAM 起始一路填充到指定地址**。

实测：把 `g_dbg` 放在 `0x2001F000`（SRAM 末尾），`ZI-data` 从几千字节**涨到 127072（124KB）**
—— 我们的全局变量其实只有几百字节，多出来的全是填充。F407 总共才 192KB SRAM，白占 124KB。

**放 CCM 起始地址（`0x10000000`）→ 填充量为 0** ✓ 实测 ZI 降到 2976。

### 为什么用固定地址
不用查 `.map` 文件就能读：`STM32_Programmer_CLI -c port=SWD mode=hotplug -r32 0x10000000 <字节数>`。

### 结构体设计的两个保险
1. **`magic` 魔数**（`0xCA7DB001`）—— 读到了才说明地址对
2. **编译期长度检查**：
   ```c
   typedef char _dbg_size_check[(sizeof(dbg_t) == 136u) ? 1 : -1];
   ```
   改了结构体忘同步读法 → **直接编译报错**

### ⚠️ 它不清零
CCM 掉电不清，所以 `main` 开头要 `memset(&g_dbg, 0, sizeof(g_dbg))`
—— 否则会读到**上次运行的残留值**（实测过：`loops` 显示 24 亿）。

## 五、`sys_tick_init()` 的两个细节

### 为什么 `LOAD = CPU_MHZ * 1000 - 1`
SysTick 从 `LOAD` **递减到 0**，一共走 `LOAD + 1` 个数。要 168000 个周期（1ms @168MHz）
就得写 **167999**。（计数器类外设的经典 off-by-one。）

### `VAL = 0` 只在开机用一次
把可能残留的计数值清掉，让第一次中断的时机准确。**之后永远不用再碰** ——
计数器递减到 0 后**硬件自动重装载**，无限循环，不需要软件干预。

---

## 六、⭐ `sys_elapsed()`：为什么用差值比较

```c
return (uint32_t)(g_ms - from_ms) >= ms;
```

`g_ms` 是 `uint32_t`，最大 42.9 亿毫秒 ≈ **49.7 天**，溢出后归零。

**差值的妙处**：无符号减法**天然回绕**，过零那一刻差值照样正确。

举例（假设上限是 10）：
```
from = 8,  现在 g_ms = 2 (已经绕过一圈)
2 - 8 = -6  →  无符号回绕  =  4     ← 实际经过的确实是 4
```

**绝对比较会误判**：`g_ms >= from + ms` 在溢出点附近得出相反的结论。

**⚠️ 所以：凡是判"过了多久"都用这个函数，别自己写比较。**
（真踩过：先写了 `g_ms >= IMU_WAIT_MS`，属于有问题的那一类，只是要连跑 49.7 天才暴露。）

---

## 七、`g_ms` 为什么必须 `volatile`

中断里改它（`cat_it.c` 的 `SysTick_Handler` → `sys_tick_isr()`），主循环读它。

不加 `volatile` 的话，编译器**不知道中断会改它**，可能把 `while (g_ms < 1000);`
优化成"读一次存寄存器，无限循环"。

---

## 八、中断开销实测

SysTick 每 1ms 中断一次，每次开销：
```
压栈 8 个字(32 字节) + 执行 g_ms++ + 出栈  ≈ 0.2 µs
```

50Hz 主循环一拍 20ms，期间 20 次中断 → 共 **4µs = 一拍的两万分之一**。可以忽略。

**换来的是"时间感"**：能判超时、能卡节拍、能检测失联。
