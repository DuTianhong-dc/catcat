# IMU 驱动说明（cat_imu.c / cat_imu.h）

> 代码里只留"做什么 + 关键约束"，为什么这么做、踩过什么坑都记在这里。
> 协议原文见 `通信协议.txt` 第四章。

---

## 一、模块特性：它是"主动上报"的

**跟舵机完全相反**：舵机是问答式（不问不说），IMU 是**上电后自己按频率往串口推数据**。

所以开发板侧的主要工作是"**收帧 → 校验 → 取最新**"，不需要每拍都发指令。
只有配置类操作（改频率、改算法、校准）才需要发指令。

**出厂默认 25Hz**（可用 `0x60` 指令改 10~100Hz），模块规格写的"启动时间 5000ms"。

---

## 二、环形接收缓冲（`rx_buf`）

### 为什么用中断 + 缓冲，而不是轮询

IMU 100Hz（10ms 一帧）而主循环 50Hz（20ms 一拍）。如果主循环直接去读串口，
**等待期间 CPU 全空转**，而且万一主循环卡一下就会丢数据。

所以：**中断里只把字节塞进环形缓冲，解析放主循环**。
中断停留最短（几十个周期），不跟 50Hz 控制环抢时间。

### 为什么满了丢【最旧】而不是丢新

- **丢新**（`if (缓冲没满) 才存`）：一旦主循环卡顿，缓冲满了之后**新数据全被丢**，
  解析出来的永远是那批旧数据 —— 而且**不报错**，读数会静默变陈旧。
  （第一版就是这么写的）
- **丢最旧**：保证最新字节一定能进来。代价是可能丢掉某帧的头（半帧），
  但状态机靠 `7E 23` 会自己重新同步，下一帧补上。

**结论**：丢旧只是"丢一帧"，丢新是"一直吃旧数据"。

### 缓冲大小 256 字节

一帧最长 21 字节（气压计），256 能存约 12 帧。
按每拍来 2 帧算，能扛住连卡 6 拍。

---

## 三、解析状态机：为什么要"排空"

`imu_poll()` 是 `while (rx_r != rx_w)` —— **把缓冲里的字节全部跑完**，不是"只吃一帧"。

**必须排空的原因**：100Hz 生产 vs 50Hz 消费，每拍积 2 帧。只吃一帧会**越积越多直到缓冲满**。

**排空的额外好处**：同一拍里同类数据解析 2 次，**后一帧覆盖前一帧** →
天然实现"只保留最新"，不需要额外的逻辑。取数函数读到的永远是最后一个完整帧。

## 四、⭐ "等包头 2"那一步的特殊处理

```c
if (idx == 1u){
    if (b == IMU_HEAD2)      buf[idx++] = b;      /* 匹配 */
    else if (b == IMU_HEAD1) { /* 留在 idx=1 */ }  /* 还是包头 → 当作新的包头1 */
    else                     idx = 0u;             /* 噪声 → 复位 */
}
```

**为什么不直接复位**：

假设总线上出现 `... 0x7E(噪声) | 0x7E 0x23(真帧头) ...`：

| 做法 | 结果 |
|---|---|
| **直接复位**（官方实现）| 第二个 `0x7E` 被当成"上一个包头的第二字节"，判不是 `0x23` → 复位；<br>等真正 `0x23` 来时状态机已经不等包头了 → **真帧的包头被吃掉，白丢一整帧** |
| **保持 idx=1**（我们的）| 第二个 `0x7E` 当前一帧头 → 保持等待 → 下一个 `0x23` 匹配 ✓ **一帧不丢** |

**实测**：这个场景在噪声里很常见（见 PC 端测试用例"噪声后重同步"）。

## 五、⭐ `imu_ensure_rate()`：为什么要单独确认频率

### 问题
`imu_init()` 末尾会发一条"设 100Hz"，但那是**模块刚上电时**发的，**可能丢**。

### 而且资料没说"输出频率是否掉电保存"
`通信协议.xlsx` 只写"默认 25Hz，可设 10~100Hz"，**没说存不存**。

### 所以不赌：等模块真在出帧了，实测一下
- 数 200ms 内进了多少帧
- 理论该来 ≈60 帧（100Hz × 3 种帧 × 0.2s），**下限取 30**（打对折容错）
- 不够快 → 补发一条"设 100Hz"

### 实测结论（2026-09-25 真机）
**`imu_rate_fix = 1`** —— 确实补设过一次 ✓
→ **输出频率不保存**，`imu_init()` 里那条每次都丢，**必须靠这个函数补**。

### ⚠️ 必须放在"确认模块已就绪"之后调
放在 `imu_init()` 里发会丢（模块还没醒）。我们的做法是放在 `boot_wait_ready()` 之后。

## 六、⭐ `imu_get_grav()` 公式的来龙去脉

### 它算什么
**世界坐标系的 -Z 方向（重力方向）在机体坐标系下的单位向量** —— 观测 `obs[6:9)`。

静止正立时 ≈ `[0, 0, -1]`；与训练的 `get_gravity() = R^T·[0,0,-1]` 同义。

### 公式与推导
```c
out[0] =   2*(w*y - x*z);
out[1] =  -2*(y*z + w*x);
out[2] = -(1 - 2*(x*x + y*y));
```
来源：四元数转旋转矩阵 `R` 的第三行取负，即 `-R[2][:]`。

### ⚠️ 与第一版的公式不同（两者是共轭关系）
| | x 分量 |
|---|---|
| 第一版 | `-(2*(x*z + w*y))` = `-2xz - 2wy` |
| 我们 | `2*(w*y - x*z)` = `2wy - 2xz` |

**把第一版的公式代入四元数共轭 `q*=(w,-x,-y,-z)`，正好得到它** —— 说明第一版隐含"世界→机体"的约定。

**谁对取决于模块输出四元数的约定**。我们采用**标准推导**（与训练侧对齐）。

### 实测验证（2026-09-25 真机）
```
grav = [-0.0053, -0.1209, -0.9926]   |grav| = 1.0000
```
- **模长精确到小数第 4 位** ✓
- 静止时 ≈ `[0,0,-1]`（正立）✓
- 欧拉角交叉印证：`roll=-4.4° / pitch=+6.9°` 与 gravity 推出的倾斜角吻合 ✓

**结论：这套公式在真机上是对的。**

### 仍待校准的一项
**模块自身坐标轴与机身的安装方向**。若不对齐，需在此加一次性旋转修正。
**自校验办法**：静止时**加速度计单位向量 ≈ -gravity**（`0x04` 帧的 accel 可拿来对，不用额外接线）。

## 七、⚠️ "还没收到帧"时的假象

`g_quat` 初始全 0，代进 gravity 公式会算出 `[0,0,-1]` —— **看起来完全像"正立姿态"，其实一个数都没有**。

**所以必须先看 `imu_get_frames()` 有没有在涨，再采信取数结果。**

（同类坑：舵机那边"`pos == 0` 也可能是没读到"。）

## 八、官方参考实现的 3 个坑（我们改掉了）

资料包里 `STM32\USART\BSP\mcu_model\imu_uart_driver.c` 是官方驱动，**3 处照抄会出事**：

1. **中断里死等**：`while (RXNE == RESET);` —— 中断本来就是 RXNE 触发的，这句多余且可能死锁
2. **攒够 127 字节才推缓冲**：IMU 一帧才 17~21 字节 → **滞后 6~7 帧**；数据流停下时最后那批永远不处理
   → 改成"**每收到一个字节就推进缓冲**"
3. **状态机"等包头2"时直接复位**：噪声夹 `0x7E` 会吃掉真帧包头（详见第四节）

## 九、数值换算

| 量 | 缩放 | 单位 |
|---|---|---|
| 加速度 | `16 / 32767.0` | g（量程 ±16g）|
| 角速度 | `(2000/32767.0) × (π/180)` | rad/s（量程 ±2000°/s）|
| 磁力计 | `800 / 32767.0` | uT |
| 欧拉角 / 四元数 | 本身就是 float32，**不用乘** | **欧拉角单位是弧度** |

**数据区从下标 4 开始**（包头1/包头2/长度/功能字 占了下标 0~3）。

---

## 十、通信参数

- **USART2 / PA2(TX)-PA3(RX) / AF7**
- **115200 8N1**（`BRR = 42MHz/115200 = 365`，误差 0.114%）
- 接收中断优先级 **6**（低：数据不紧急，缓冲能扛几十毫秒）
- **接线是交叉的**：模块 RX → PA2、模块 TX → PA3

---

## 十一、⭐ "帧率" ≠ "输出频率"（+ `g_frames` 是 16 位，会回绕）

模块**每个周期推 3 类帧**（`0x04` 原始 / `0x16` 四元数 / `0x26` 欧拉角）→

```
帧率 = 3 × 输出频率          100Hz → 300 帧/s
```

**实测（2026-09-27，两次读数取差）**：

```
Δ1296 帧 / Δ4.320 s = 300.0 帧/s  ÷ 3 = 100.0 Hz   ✅
```

频率设置本身没问题：厂商 `通信协议.xlsx`（`6.附件/通信协议/`）里
`0x60 设置数据输出频率` = **参数1 是 Hz、范围 10~100、参数2 固定 `0x5F`、无返回**，
我们发的 `{100, 0x5F}` 完全一致；"默认 25Hz，不保存" 也靠 `imu_ensure_rate()` 每次上电补设 ✓

### ⚠️ 坑：`g_frames` 是 `uint16_t`，跑 ~3.7 分钟就回绕

300 帧/s → 65536 帧只需 **218 秒**。所以 `g_dbg.imu_frames` 里的数**不能当"累计帧数"**去
除总时长算频率 —— 过回绕点会读出 **293 / 137** 这种假数（今天就先后被骗了两次）。

| 用法 | 行不行 |
|---|---|
| 驱动内部"两次读差值 > 0 = 有新帧" | ✅ u16 够 |
| `imu_ensure_rate()` 数 200ms 窗口内的帧数 | ✅ 窗口短，不会绕 |
| **`read_dbg.py` 用"累计值 ÷ 总时长"** | ❌ 已改成**内部隔 1s 读两次取差** |

**若想让观测区直接有个可信的累计帧数** → 固件侧改成 u32 自加（1 行，待定，别急）。
