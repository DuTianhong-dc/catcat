## 一、要不要为动作模块新建一种指令包类型？

**结论：不新建"帧类型"，只新增"子类型"。** 帧壳直接复用现有的 `0xCC` 变长帧。

### 1.1 现状盘点

| 层 | 现成的东西 | 位置 |
|---|---|---|
| 帧壳 | `0xCC \| len \| 载荷 \| ck`（len ≤ 96，载荷首字节 = 子类型） | v2 `cat_esp32.c` 已实现收帧状态机 + `esp32_ota_fetch()` 取帧 |
| 动作子类型 | `0x10 BEGIN / 0x20 FRAME / 0x30 END / 0xF0 ACK`（v1 已定义并跑通过） | v1 `cat_ble_proto.h` |
| 策略子类型 | `0x70 BEGIN / 0x71 DATA / 0x72 END / 0x73 ABORT / 0x74 STAT` | v2 `cat_polupd.h`（沿用 v1 编号） |

子类型空间事实上已经分域：`0x10~0x3F` 动作 / `0x50~0x5F` 维护 / `0x60~0x6F` 配置 / `0x70~0x7F` 策略 / `0xF0+` 应答。
**动作与策略各有各的号段，同走一条物理通道、互不干扰。**

### 1.2 不新建帧类型的四条理由

1. **帧壳是链路层资产，重复实现是浪费**：收帧（找头/长度/校验和/丢弃坏帧）已在 `cat_esp32.c` 里做完并被真机验证过。新建帧类型 = 再写一套同样的状态机 + 再占一块接收缓冲，收益为零。
2. **容量够用**：动作 FRAME(v3) 整帧 = `CC 45 20 <68B> ck`，len = 69 ≤ v2 的 `ESP32_OTA_MAX = 96`。**无需扩任何缓冲。**
3. **分层干净**：帧类型（首字节分流）属于链路层；"这帧是干什么的"属于子类型，由编排层分派。新建帧类型等于把业务语义下沉到链路层，破坏现有分层。
4. **与既有生态字节级兼容**：v1 的 PC 工具 `send_action_ble.py` 已经按 `CC 01 10 ck / CC 39 20 <56B> ck / CC 01 30 ck` 打包并跑通真机。复用帧壳 = 工具链零改动，CSV→帧的转换逻辑原样可用。

### 1.3 真正需要新增的东西（三条，都不是"帧类型"）

| # | 新增项 | 位置 | 说明 |
|---|---|---|---|
| ① | **子类型分派** | `main.c` 编排层（0b 段） | v2 现在把**所有** `0xCC` 帧直接喂给 `cat_polupd_frame()` —— 动作帧会撞上它的 `default` 分支返回 `POL_RC_BAD_HDR`。必须在 main 里按 `d[0]` 分派：`0x10/0x20/0x30` → cat_action，`0x70~0x74` → cat_polupd |
| ② | **cat_action 模块**（新文件） | `cat_action.c/h` | 从 v1 移植 + 适配 v2（无 FSM → 改为门控，见 §4） |
| ③ | **ACK 编号** | `cat_action.h` | ⚠️ **2026-10-03 实施时修正**：原稿写"沿用 v1 的 `0xF0`"是错的 —— v1 的 `0xF0` 是 **0xCC 帧内的子类型**，而 v2 的上行改用了 **`5A A5 \| len \| type \| 载荷 \| ck`** 帧壳（`esp32_send_up`），ACK 编号属于**上行帧的 type 字段**，与 v1 不同层。现定 **`ACT_UP_ACK = 0x78`**（避开 OTA 的 `0x76`/`0x77`），载荷 = `rc(1) + 表内帧数(1)` |

> 可选重构（**不属于本设计必做项**）：`cat_esp32` 里 `ESP32_OTA_*` / `esp32_ota_fetch()` 的命名绑定了 OTA 语义，
> 现在两个业务共用。若要改叫 `ESP32_VAR_*` / `esp32_var_fetch()`，改动点在 cat_esp32.h/.c + main.c×2 —— 建议**先加注释**（"变长帧通道，策略 OTA 与动作加载共用"），改名留到下次顺手做。

## 二、CSV 字段设计方案

### 2.1 一个关键分工（先明确，避免误读）

> **固件不解析 CSV。** CSV 是 **PC 侧**的输入格式；PC 工具读 CSV → 校验 → 逐行打包成 0xCC FRAME 二进制帧 → BLE 下发。
> 理由：① 固件省掉文本解析代码与 float 字符串转换 ② 与策略 OTA 同构（同一条链，同一套停等/ACK 节奏）
> ③ kfkit 关键帧编辑器输出的就是 CSV，PC 侧直接消费。

### 2.2 列定义（共 17 列；与 v1/v3、现有 kfkit 工具链完全一致）

| # | 列名 | 含义 | 数据类型 | 必填 | 取值 / 格式约束 |
|---|---|---|---|---|---|
| 1 | `seg_s` | 从上一帧插值到**本帧**的时长（s） | float | ✅ | `0.05 ~ 25.0`；越界整帧拒收 |
| 2 | `hold_s` | 插值到位后**保持**的时长（s） | float | ✅ | `0.0 ~ 25.0`；越界整帧拒收 |
| 3~14 | `j0` … `j11` | 12 个**主动关节角**（rad，**绝对角**，顺序 = 观测序：后右 3 / 后左 3 / 前右 3 / 前左 3，每腿 髋侧摆→髋俯仰→膝曲柄） | float | ✅ | 理论 ±3.0；**超出关节限位由固件钳位**（不拒帧）；含 NaN 整帧拒收 |
| 15 | `torque` | 0x30 转矩限制 | float | ⭕ 可选 | `0 ~ 1000`（1000 = 100%，即不限制）；缺省 **1000** |
| 16 | `speed` | 0x2E 运行速度 | float | ⭕ 可选 | `0 ~ 3400`（步/s；**0 = 最大速度**）；缺省 **0** |
| 17 | `acc` | 0x29 加速度 | float | ⭕ 可选 | `0 ~ 254`（0 = 最大）；缺省 **0** |

> ⚠️ **2026-10-03 实施时修正**：后三列的**传输类型是 float32**（不是整型）—— v1 的 FRAME 载荷
> 是"14/15/17 个 **float32**"（56/60/68 字节 = 个数 ×4），所以 CSV 里写成整数或小数都可以，进帧统一按
> float32 编码、固件侧再钳成整型档位。CSV 的"取值"语义仍是整档（1000/300/10 这种写法）。

**语义补充（三条容易踩的）**：
- **`j*` 是绝对关节角，不是"策略动作"，也不是"相对站姿的偏移"**。它直接对应 MuJoCo `qpos` 里那 12 个主动关节，
  也就是 kfkit 编辑器里摆出来的角度。固件侧用它做逆换算 → 舵机计数时，**复用 `obs_act_to_counts` 里那段
  逆变换**（`counts = ZERO + q×DIR/r2r`），不要另写一套公式（两处口径必须同源）。
- **必需列是 14 列**（`seg_s, hold_s, j0..j11`）；后 3 列可整列省略。允许的文件形态：**14 列 / 15 列（+torque）/
  17 列（+torque speed acc）**，与 v1 的"按载荷长度识别 v1/v2/v3"一一对应。
- **同一文件内列数必须一致**，混用直接报错（PC 侧检查）——列数不同意味着帧载荷长度不同，固件按长度识别版本，混发会错。

### 2.3 示例（取自真实文件 `_action_lie_v3.1.csv`，17 列）

```
seg_s,hold_s,j0,j1,j2,j3,j4,j5,j6,j7,j8,j9,j10,j11,torque,speed,acc
0.1,0.1,0,-0.0476,1.04,0,0.0476,-1.04,0,0,0,0,0,0,200,0,10
2,1.5,0.7055,-1.1095,-0.1388,-0.6998,1.1105,0.1384,0.5485,-1.0448,-0.1389,-0.5438,1.0869,0.139,200,300,0
2,0.5,0,-0.0476,1.04,0,0.0476,-1.04,0,0,0,0,0,0,500,0,0
```

第 1 行 = 表头（PC 跳过，不下发）；第 2 行起每行 = 一个关键帧。
本例：**3 个关键帧**（0.1s 微调 → 2s 翻躺 + 保持 1.5s → 2s 回站 + 保持 0.5s），真实播完约 **7.0s**
（= 进场 0.8 + Σ(seg+hold) 6.2 + 出场 0.8，见 v1 `cat_action_total_s()`）。

### 2.4 文件命名与编码约定

| 项 | 约定 | 理由 |
|---|---|---|
| 命名 | `<动作名>_v<主>.<次>.csv`（如 `lie_v3.1.csv`）；文件名即动作名，**不再单设"动作名列"** | 一次加载 = 一张表 = 一个动作；不需要额外的 ID 字段 |
| 目录 | 生成端 `mujoco/tools/kfkit/keyframes/`；待发目录 `mujoco/play/` | 沿用现状，不加新目录 |
| 编码 | **UTF-8 无 BOM**（规范）；解析端必须容忍 `utf-8-sig`（带 BOM 也能读） | 现有工具已是 `encoding="utf-8-sig"` |
| 换行 | **LF** 为规范；**CRLF 必须容忍**（Excel 另存为会带 CRLF+BOM） | 手工改表最常见的坑 |
| 分隔符 | 半角逗号 `,`；**不接受中文逗号** | — |
| 注释 | `#` 开头整行 = 注释，PC 跳过；空行跳过 | 现有工具已支持 |
| 表头 | 允许有（推荐有）；PC 侧"非数值行自动跳过"，**固件侧完全不关心** | 表头不入帧 |
| 数值格式 | 十进制，可带负号/小数点（`-1.1095`、`2`、`0.139` 均可）；**科学计数法不推荐**（Python 可读，但手改易错） | — |
| 行数上限 | **≤ 64 帧**（= v1 `ACT_RAM_MAX`，约 4.6KB RAM） | 超出 PC 侧直接拒，别发到一半才发现 |

## 三、指令包 ↔ CSV 的对应关系

| CSV 侧 | 二进制帧 | 载荷 / 参数 | ACK 里的 `n` |
|---|---|---|---|
| （会话开始） | `CC 01 10 ck` BEGIN | 无 | `0` |
| 第 1 个数据行 | `CC 45 20 <68B> ck` FRAME | 子类型 + **17×float32，顺序 = `j0..j11, seg, hold, torque, speed, acc`** | 加载后帧数 |
| …第 k 行 | 同上（每行一帧） | 同上 | `k` |
| （文件结束） | `CC 01 30 ck` END | 无 | 总帧数（**PC 用它核对"CSV 行数 == 固件实收帧数"**） |
| 出错 | — | — | `5A A5 \| len \| 78 \| rc, n \| ck`（v2 上行壳） |

> ⚠️ **两个必须记住的对应关系（2026-10-03 实施时确认）**：
> 1. **帧内字段顺序 ≠ CSV 列顺序**。CSV 是 `seg_s, hold_s, j0..j11, …`，而帧载荷是
>    **`j0..j11, seg_s, hold_s, …`**（v1 既有约定，v2 沿用 —— `cat_action.c` 里按此解析）。
>    **重排由 PC 侧完成**，固件不做文本/列序处理。
> 2. 17 列形态整帧 = `CC 45 20 <68B> ck` = **72 字节**，与 v1 的 `BLE_LOAD_MAX_FRAME_BYTES 72` 一致；
>    仍 ≤ v2 `ESP32_OTA_MAX = 96`，**无需扩缓冲**。

**一一对应关系**：
- **1 个 CSV 数据行 ↔ 1 个 FRAME 帧**（顺序即时间轴顺序，不可乱序——固件按字节序收，不做重排）
- **1 个 CSV 文件 ↔ 1 次加载会话**（BEGIN → N×FRAME → END）= 固件里的一张 RAM 关键帧表 = **一个动作**
- **表头行 / 注释行 / 空行 ↔ 不下发**

**返回码（沿用 v1，与 `cat_action_load_frame()` 返回值对齐）**：
`0 OK` ｜ `1 表满(>64)` ｜ `2 seg 超范围` ｜ `3 hold 超范围` ｜ `4 含 NaN` ｜ `5 长度非法` ｜ `6 校验和错` ｜ `7 子类型未知` ｜ `8 顺序错(未 BEGIN 就 FRAME)`

## 四、整体下发流程

### 4.1 要不要走"更新模式"（KEY0）？

**不需要。** 动作表存 **RAM**（64 帧 × 64B ≈ 4KB），**不擦不写 Flash** —— 而 v2 之所以要"更新模式"，
是因为**策略 OTA 擦 2×128KB 扇区要 1~4 秒、期间会被 IMU 中断风暴打死**（09-30 真机实锤）。
动作加载全程只写 RAM，耗时 ≈ 64×72B/115200 ≈ **40ms**，与 IMU 互不干扰。

**但要设"操作门卫"**（对应 v1 的维护模式门卫）：加载期间**要求 `enable=0`（未使能）+ 无故障**——
"站着不动时才能换动作表"。理由：换表瞬间会清表重建，若此时猫在走，随后 END 触发的播放会从行走姿态
突然切到首帧，是危险跳变。

### 4.2 时序（推荐方案 A：END 即请求播放 + 门控受理）

```
PC (send_action_ble.py 扩展)                 STM32 固件
─────────────────────────────────────────────────────────────────────
读 CSV → 校验(列数/范围/NaN/≤64行)
  │
  ├─ CC 01 10 ck ─────────────────────────→  main 分派 → action_load_begin()
  │                                          ←── 5A A5 02 78 00 00 ck      (rc=OK, n=0)
  ├─ CC 45 20 <68B> ck  (CSV 第 1 行) ─────→  action_frame → action_load_kf()
  │                                          │  逐关节钳到限位; NaN/超时长 → rc≠0
  │                                          ←── 5A A5 02 78 00 01 ck      (rc=OK, n=1)
  ├─  …(每帧等 ACK 再发下一帧, 停等)…
  ├─ CC 45 20 <68B> ck  (CSV 第 N 行) ─────→  …
  │                                          ←── 5A A5 02 78 00 N ck       (n=N)
  └─ CC 01 30 ck ─────────────────────────→  action_frame → 锁定表(空表则 rc=ORDER)
                                             ←── 5A A5 02 78 00 N ck  ★PC 核对 N == CSV 行数
                                                    ↓
                                     (下一轮实现) 编排层每拍检查:
                                       action_ready() && 上网门卫?
                                         ├─ 是 → 播放: 动作输出 → obs_rad_to_counts → 舵机目标
                                         └─ 否 → 不播(表留在 RAM, 等下次)
```

**要点**：
- **每帧等 ACK**（停等）：① v1 既有约定（v2 的 256B 环形缓冲能装 3 帧，但停等最稳）② ACK 里的 `n` 让 PC 逐帧核对
- **END 只"锁定 + 请求"**，真正开始播由编排层按门卫条件放行 —— 这解决了 v2 无 FSM 后的"谁受理"问题
- **播放期间策略输出被忽略**（动作优先），但**安全链不动**：故障 → 立即 `abort()` + 平滑回站姿 + 后续走既有卸力路径

### 4.3 播放器行为（移植 v1，四条必须保留）

| 行为 | 参数 | 说明 |
|---|---|---|
| 进场插值 | 当前角 → 首帧，**0.8s** | 保证从"现在在哪"平滑切入，不跳变 |
| 帧间插值 | **smoothstep**，`seg_s` 时长 | 按 `lerp_write()`：每拍限速 **5.0 rad/s**（v3 从 3 提到 5）+ 限位截断 |
| 出场插值 | 末帧 → **默认站姿**，0.8s | 播完自动回站姿，且恢复运动参数档位（torque/speed/acc 回默认，防后续被限流） |
| 中断安全 | `abort()` + `last_pose()` | 故障/急停中断时**不能直接切站姿**（会 12 颗全力冲）；要用 `last_pose` 做平滑过渡起点 |

### 4.4 备选方案 B：新增 `0x31 PLAY` 显式触发

`END` 只锁定不播；PC 另发 `CC 01 31 ck` 才播。**取舍**：

| | A（END 即请求，门控受理） | B（显式 PLAY） |
|---|---|---|
| PC 工具改动 | 零（v1 就是这语义） | 需加一步 |
| 时序确定性 | 弱（"条件满足才播"，PC 不知道确切起播时刻） | 强（发 PLAY 即播，可回 ACK 报起播） |
| 与 v1 一致 | ✅ | ❌ |

**推荐 A**（与 v1 工具链零改动，"挂起"只在忘开使能时出现，实测场景很少）；若以后要"定时/同步多机播放"再补 B。
